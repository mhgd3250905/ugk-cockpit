# MCP 认证恢复：同路径不同凭据文件 · 2026-09-05

## 故障与已证实原因

原 ZCode 手腕聊天在 Cockpit 更新、重启后，调用 `ugk_work_relay`、`ugk_work_context` 持续返回“本地控制台身份已失效”。工作会话本身仍为 active、revision 17，认证失败发生在会话及 revision 检查之前。

最初发现入口只在启动时读取 `api-token`，显式本地凭据遇到 401 不会重读。版本 `97ceec1` 已加入一次重读重试，但没有解决本次原聊天故障：11:15 新启动的 MCP 进程在 11:16 仍然失败。

随后对真实进程进行了临时诊断，未输出或保存凭据原文：

- ZCode 日志把原聊天连接 `35d82452-6ddf-4b58-aa72-8307a69f6555` 明确关联到 MCP PID 51912。
- 该进程加载的 `service-client.mjs` 与磁盘修复版本一致，工作目录为原手腕项目，Node 为 24.15.0。
- 11:30 原聊天实际调用 `/api/v1/mcp/work/context`，地址为 `http://127.0.0.1:41737`，收到 401。发送的凭据与该进程重新读取的文件一致。
- 两边解析出的路径均为 `C:\Users\29485\AppData\Local\UGK Cockpit\api-token`，但 ZCode 看到的文件 ID 为 `22236523161000041`，诊断进程看到的文件 ID 为 `6192449488663425`；在进程内部比较凭据摘要的结果为不相同。
- 同时，诊断进程使用自己读取的凭据请求当前服务，HTTP 200、项目数 6；ZCode 进程使用自己读取的凭据请求同一服务，仍为 401。

因此，已证实的直接原因是**两个进程在同一路径下看到不同的凭据文件**。MCP 启动入口错误地假设客户端能读取到服务正在使用的那份文件；反复重启、重新读取客户端文件均不能纠正这一差异。

造成文件视图分离的具体 Windows 机制、操作方及时间尚未查明。本记录不把它归因于某个 Agent、ZCode 缺陷或用户操作，也不把此前数据库句柄异常直接当作本次认证问题的已证实因果链。

## 修复

`src/mcp/main.mjs` 不再读取 AppData 的服务私有凭据，统一使用服务已有的本机 MCP 认证入口 `/api/v1/mcp/session`。凭据来自实际连接的服务实例，限定于 MCP API，不用于 dashboard 等普通管理 API。

复用 `service-client.mjs` 已有的续期机制：收到 401 后重新申请一次 MCP 凭据，原样重发业务参数。不会重新 init，不会更换 `clientRequestId` 或 `expectedRevision`，不会清空进程内工作会话绑定，也不增加不确定网络结果的自动业务重试。

这不是在显式本地凭据校验失败后降级绕过认证；产品入口从建立连接时就使用既有 MCP 认证方式。显式传入本地凭据的库调用行为仍保持原约束。

## 原聊天验收

仅重载了已核实的手腕 MCP 子进程。Cockpit 服务 PID 3128、ZCode 原聊天和其他项目进程均未重启。

ZCode 在原连接上自动重新连接并加载 MCP PID 46360。用户在原手腕聊天再次调用 `ugk_work_context({})`，确认调用成功，仍返回原 active 会话、revision 17、租约持有中。

返回 `bindingStatus: unbound`、`requiresUserConfirmation: true` 是桥接进程重载后的正常确认要求，不是认证失败。用户尚未在这一步确认绑定；本次修复没有代 ZCode 确认、提交 Relay 或生成 continueCode。

## 防止复发的检查

- 不再以“绝对路径相同”证明跨进程凭据一致，也不复制服务私有凭据给客户端。
- 独立 HTTP 请求或新 stdio 进程成功，不能替代原聊天验收；关联实际连接、进程与调用结果。
- 新增入口回归：即使客户端 AppData 存在另一份有效长度凭据，也使用服务签发的 MCP 凭据，并在失效后原样续期请求。
- 新增真实临时 HTTP 服务回归：同一个 handler 在服务重启后经历 401、重新获取凭据、通过认证；业务参数校验仍生效，不创建工作会话。
- 临时运行时探针已移除，诊断监听端口已关闭。运行中的数据库或凭据文件不作替换、清理或覆盖，维护要求继续遵循 [本地服务恢复记录](LOCAL_SERVICE_RECOVERY.md)。
