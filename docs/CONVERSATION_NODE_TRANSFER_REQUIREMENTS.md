# 会话节点追溯与平台授权转交：需求与回归风险评估

日期：2026-09-07。代码评估基线：`c004dd5`。

状态：**schema 25 本地验收、服务部署及已安装技能切换完成；当前 Codex 原聊天只读恢复通过，ZCode 现场验收待执行**。本文记录需求及风险依据，当前实现契约见 `CONVERSATION_DURABILITY.md`。部署未转交或重建真实业务会话；具体通过范围见第 9 节及 [部署记录](LOCAL_SERVICE_RECOVERY.md)。旧宿主缓存的工具定义仍需重连加载。

## 1. 目标与已确认语义

用户需要知道最后一次有效工作流操作由哪个聊天完成；走错聊天时明确指向正确节点；原聊天不可用或用户已在其他位置继续工作时，必须由用户在工作台授权重新接手。

- 节点不限于代码成果。成功接入、进展、准备接力、接力接收、接手及结束等改变工作流状态的操作都形成相应节点。
- `A → A1 → A2 → A3 → C 接手`：接手成功时最新节点就是 C，不能等 C 提交代码后才算 C。
- C 接手节点引用 A3 的前序节点；A3 的成果归属不改写。后续 C 进展接在 C 的接手节点后。
- 只读 context、轮询、预检、被拒请求、未提交的确认提示不推进工作链；拒绝及失败可进入独立审计/诊断记录。幂等重放返回原节点，不重复追加。
- 每个 AI 操作节点必须记录平台及宿主会话 ID。名称、创建时间是可选定位信息，不作为本阶段必填业务参数，不得编造。
- 正常 Relay 保留；异常接手必须从工作台授权，不能仅凭 MCP 聊天中的“用户已同意”完成。

## 2. 范围与对象

“接在最后节点之后”作用于**明确的工作链/工作会话及工作副本**，不是整个项目唯一一条全局链。同一项目已有多工作副本、多工作链、active/standby、主会话审核与独立送审能力必须保留。项目总览可按时间展示多链事件，但总览排序不能决定某条链的权限。

区分字段命名：宿主聊天 ID（如 ZCode 的 `sess_…`）不等于 Cockpit 工作会话 `sessionId`。身份标识采用平台命名空间＋宿主聊天 ID；模型型号、工具连接 ID、PID、路径不作为聊天身份。

节点中记录：稳定 nodeId、所属链、前序节点、节点类型、操作者类型（AI/用户/系统）、AI 平台与宿主聊天 ID（适用时）、服务端提交时间、关联业务命令/回执、成果或原因引用。已有事件能够提供这些事实时优先复用，不另外复制一套不可同步的时间线。

## 3. 身份输入契约

### 必须达到的行为

1. MCP 操作关联平台与宿主会话 ID，优先由宿主请求元数据/适配层自动传递；同一 MCP 进程承载多聊天时按每次请求取值。
2. 服务端保存身份、来源及核验方式，身份连续性不依赖模型记忆、连接缓存或项目里的共享凭证文件。
3. 同聊天重启保持身份；分叉、新聊天、同目录另一个聊天不得继承旧身份；平台相同但会话 ID 不同的调用者必须隔离。
4. 身份缺失或冲突时保留查询能力，明确提示适配/识别问题，不根据目录、最新聊天、时间或任务描述猜测。
5. title 可改名，时间可能未知；改名不转移授权。用户可复制平台与会话 ID 到对应宿主追溯，不要求本阶段实现深链接或读取聊天全文。

### 接入证据与现场验收边界

用户提供的 ZCode 观察表明可以从任务输出位置取得 `sess_…`，再只读查询宿主数据库标题。本轮进一步从本机安装代码查明 ZCode 的原生 `_meta['com.zcode/request-context'].session_id` 及镜像字段传递机制，并接入解析；Codex 使用原生 `_meta.threadId`，通用适配继续支持命名空间身份。多个身份来源冲突时拒绝，不静默选取。

**代码机制查明不等于原宿主现场验收。** 原 ZCode 聊天仍需验证实际请求、重启、并行聊天、分叉和共用 bridge；用户提供的 ID 未被当作已验证的实时调用身份。普通 scoped MCP 状态写入已要求可靠宿主身份，旧 connection-only owner 只读保留，不再通过旧聊天内确认继续写入。

若只能让 Agent 在普通参数里填写 ID，它首先是声明的归属信息，不得自动等同于宿主确认的调用身份。知道 A3 的 ID 不等于拥有 A3 权限。不能为支持这一形态而直接解除现有参数防注入约束；若需新增声明式注册，必须单独设计并验证平台配对机制。无法完成可靠接入时如实标记该宿主不具备自动连续性，不能用永久 connection-only 重试替代正式验收。

## 4. 节点与当前授权的一致性

核心原则：节点记录是可追溯历史；数据库中唯一有效持有人和业务状态是当前授权事实。节点提交、持有人转移/撤销、工作状态、业务 revision 和幂等回执在同一事务内更新。

正常工作节点的操作者必须是当前有效持有人。正常接收/平台授权转交节点是显式改变持有人的状态转换，不能先按旧持有人规则拒绝所有合法接收。

| 操作 | 最新节点 | 操作完成后的接续规则 |
| --- | --- | --- |
| A3 成功记录进展 | A3 的进展节点 | A3 可继续，仍受状态、lease、CAS 约束 |
| A3 准备 Relay | A3 的待接力节点 | 等待接收，A3 不再继续开发；不能因它仍是最后操作者就放行 |
| C 成功接收 Relay | C 的接收节点 | C 可继续；A3 及更早聊天失效 |
| 用户在工作台授权异常转交 | 用户的转交授权节点，引用 A3 | 原持有人冻结，等待授权被合法消费，不向任意 AI 放开 |
| C 成功消费转交授权 | C 的接手节点 | C 可继续；旧持有人持续拒绝 |
| C 结束阶段 | C 的结束节点 | 会话已结束，不因 C 是最后操作者而继续放行 |

因此“不再有两个互相矛盾的最新节点”，不等于“只看最后一条记录的操作者就能判断权限”。节点类型与工作状态必须明确，不能重犯拿历史 Relay 代替当前 owner 的错误。

## 5. 错误聊天尝试推进

B 或 A1 操作 A3 当前持有的工作链：服务端拒绝本次工作流写入，不推进节点、不刷新业务 revision、不自动认领。

响应提供当前链定位、最新工作流节点及类型、当前可接续状态、当前持有人的平台/会话 ID、最近登记时间、可读成果摘要、明确下一步和 diagnosticId。内容按项目访问权限返回，不暴露凭据或其他无关项目记录。

提示应为“此工作链当前由 ZCode / sess_… 继续，请回到该聊天；如需更换，请到工作台授权转交”。如果只知道此前连接，明确说“此前连接，无法定位聊天”；不能声称已识别另一聊天。绑定异常、身份缺失、真实撤销分别报告，不能一律叫 replaced。

## 6. 工作台授权异常转交

用户打开项目，选择**准确的工作链与最后节点**，查看持有人及最近成果，确认“停止旧聊天后续推进，授权新的聊天接手”。工作台操作使用管理侧认证及现有同源保护；普通 MCP 凭据不能签发、取消或续期这种管理授权。

本轮按以下行为实现并验证 UI/API 契约，原宿主现场验收另行执行：

1. 以页面读取到的当前节点/授权版本作 CAS；页面过期则刷新事实并重新确认，不能授权错误的旧持有人。
2. 签发授权时原持有人立即失去推进权，链进入转交等待状态。保留原身份、节点、原因、确认时间和已冻结事实，不删除历史。
3. 授权限定准确链、工作会话、工作副本、签发时的授权版本及有效期，只能成功消费一次；目标身份已知时绑定目标。目标未知时给用户一份一次性接手指令，不做全局解锁；授权秘密只以安全校验形式持久保存，不进入普通日志。
4. C 从其真实身份发起消费；授权校验、旧权撤销、新 owner、C 接手节点、业务 revision 和结果回执原子提交。两聊天并发消费最多一个成功。
5. 超时只让授权失效，不开放任意接手，也不静默恢复 A3。链保持待处理，用户可以重新授权或显式取消转交。
6. 取消转交须明确是否恢复先前持有人；恢复也是新的受审计状态转换，不能倒拨 revision 或复活旧命令。授权已被 C 消费时，不能用原取消请求撤销 C，需新的用户转交操作。
7. 传输结果未知时原参数、原幂等键重试，返回既有结果；不能把已成功但回复丢失的接手再次执行。

有效期已确定为固定 **10 分钟**，不新增复杂配置。过期不得要求用户手工拼接字段。管理授权只允许浏览器同源安全会话签发/取消；MCP takeover 仅消费平台签发的 `{ sessionId, clientRequestId, transferCode }`。过期 resume 的新请求转平台授权，旧聊天内两步确认不再提供旁路；已成功的历史幂等回执保留，但不复活当前权限。

平台可以覆盖 `awaiting_resume` 工作链的待接 Relay；签发时把旧 active Relay 标为 expired 并推进 revision，取消转交也不恢复旧码。standby 与已结束工作会话仍可查看，不通过授权入口绕过原状态规则。签发旧请求被重放时，已消费/取消/过期/替代授权只显示已处理状态，不展示旧码。

此管理入口控制产品工作流，不宣称能抵御拥有本机完整权限、能直接修改数据库或操纵浏览器的恶意程序。不能把普通 MCP 调用权限当作工作台用户批准，也不能仅靠隐藏按钮实现隔离。

## 7. 持久性与迁移要求

- 身份关联、当前持有人、撤销/冻结状态、节点、授权签发/消费/取消/到期依据、幂等请求及回执全部持久化。时间依据由服务端记录，不用模型报出的创建时间决定先后。
- 过期判断必须在每次消费时依据数据库期限核验，不能依赖进程内定时器执行过。重启前签发的有效授权可恢复，过期授权不能因重启复活。
- 延续现有 SQLite 事务、revision CAS、单一有效 owner、单工作副本写 lease；不新增第二套目录凭证或跨聊天共享 bearer token。
- 历史缺少宿主 ID 的节点标记“身份未知/此前连接”；不根据同目录、任务名、时间相近回填成某个聊天。后来经过用户确认的身份关联作为新事实保存，不能把推测覆盖到旧节点。
- 当前已确认的有效绑定（包括历史 Relay 后的 takeover）必须保留；升级不能要求所有用户重做接手，也不能恢复已撤销身份。
- 迁移可重复、保留原有业务记录和幂等回执；新字段只增加确定事实。新旧 API/技能切换应先检查能力，未完成升级明确报告版本不支持，不能静默退回 MCP 自行 takeover。
- 旧的聊天内两步 takeover、context 绑定确认、过期码确认等所有可能取得写权限的入口都需逐一审计。正常已授权 Relay 恢复与异常转交分开；不能留一个旧接口绕过工作台批准。
- 受保护工作链的接手规则不能误伤现有无 init 独立送审、用户普通 Git 操作及其他工作副本。对已有 work session 的写入保持归属约束，平台登记失败不伪造本地成果失败。

## 8. 对照历史踩坑：会不会开倒车

| 历史问题/保护 | 新方案必须保留的约束 | 会导致倒退的实现 |
| --- | --- | --- |
| alpha.32 绑定仅在 bridge 内存，重启后丢失 | 平台持久身份与 owner，原聊天重启实测 | 只让 Skill 记会话 ID 或缓存到进程变量 |
| ZCode 同路径不同凭据文件导致持续 401 | 凭据从实际服务申请，身份与认证分离 | 再让 Agent 读/复制项目或 AppData 私有 token |
| 空参 context 被内部 takeover 字段组合拒绝 | 服务签发的所有合法绑定都可回读，含历史数据 | 只测无历史 init，不测接力后接手 |
| revision 41 takeover 被历史 Relay 34 误判 replaced | 统一当前 owner 判定，节点与权限事务一致 | 用最新 Relay、日志时间排序或 receipt 推算 owner |
| 旧回执展示过期写权限 | 历史结果不变，能力按当前数据库状态重算 | 幂等重放同时复活旧绑定或追加新节点 |
| 拒绝没有可关联诊断、误报其他聊天 | 区分身份缺失/撤销/状态冲突，返回诊断号 | 因没有 payload 就断言宿主换连接，或不断让用户重试 |
| 多工作副本/active 与 standby 并存 | 节点和授权按精确工作链隔离 | 整个项目仅保留一个“最后 Agent” |
| prepared 合并在拒审后恢复仍可能执行 | 恢复后在实际 Git 写入前复核归属、审核和版本 | 认为“接手成功”可绕过原审核/合并门禁 |
| 接力结果丢失、进程终止、重复消费 | 持久幂等、单事务、真实进程终止测试 | 只测试会执行 finally 的异常或重发新请求 |
| 服务读到空列表但磁盘仍有项目 | SQLite 一致性备份、核实实例及项目详情 | 覆盖运行中数据目录、重新 init、只验 HTTP 200 |
| 来源无法证明的本地改动 | 保留文件，未知归属如实标识 | C 接手就把所有现有改动记作 C 的成果 |

评估结论：方向优于当前方案，前提是可靠身份输入与管理侧授权真正落地。它补齐可追溯信息和用户恢复入口，不应推翻 `c004dd5` 的当前 owner 事实源。若仅在所有工具上新增两个模型自填参数，或把平台“解锁”做成暂时关闭权限校验，则是退步。

## 9. 实施顺序与验收

1. **身份接入证明**：先验证 ZCode/Codex 原聊天 ID 的取得与每请求传递，覆盖重启、分叉、共用 bridge、并行聊天。不能拿本机新脚本成功冒充原宿主成功。
2. **状态与数据契约**：确定工作链节点映射、授权冻结/消费/取消状态、事务与迁移；复用现有事件/回执，避免重复事实源。保留多链与未知历史。
3. **管理入口＋MCP 消费**：实现工作台授权与只允许消费的 MCP 接手，关闭旧异常接手旁路；拒绝响应能够定位正确聊天。
4. **技能与安装一致性**：提供用户可直接复制的指令，同步协议、界面文案、仓库技能和经授权安装的副本；明确服务更新与宿主加载新版 bridge 是两件事。
5. **验收后切换**：先独立审查权限/迁移路径，再最终完整门禁；实际升级按恢复文档备份并核对项目与历史，最后在原 ZCode 聊天验证。

必要验收：

- A→A1→A2→A3，B/A1 推进被拒，返回 A3 的平台/会话 ID；拒绝和只读查询不产生工作节点。
- C 接手成功就形成 C 节点，context 与实际写入均允许 C；A3 后续写入被拒。重复消费仍为同一节点。
- 工作台等待转交时 A3 冻结；授权过期、取消、并发消费、页面过期、回复丢失、同链新 Relay 均按状态和 CAS 处理，不出现无主可抢窗口。
- 旧 MCP 无管理权限；不能伪称用户批准、伪填 A3 ID、跨项目/跨工作链消费授权或通过旧接口绕过。
- 迁移前后已有历史保留；六次历史 Relay 后的 takeover、旧版持有人和未知身份记录正确处理。
- 服务/bridge 真实重建与事务提交前后进程终止，不丢 owner/待授权状态、不重复节点、不复活撤销记录。
- prepared Git 操作与撤权并发时在实际副作用前再次检查；已经发生的外部 Git 成果单独恢复，不能声称数据库事务回滚了外部写入。
- 诊断轮转与写入失败不改变业务结果；节点及授权审计不是可随诊断轮转丢弃的临时日志。
- 最终 `npm test`、`npm run test:phase0`；涉及网页则 `npm run build:web` 及平台手动授权的浏览器验证；原宿主完成全链路验收。

schema 25 已以 `commands` 操作者三列及事务内触发器维护 `work_session_nodes`；init adopted 与 handoff 合并同次逻辑节点，旧 progress 仅作身份未知的历史展示。长耗时 Git 动作在副作用前再次核验当前权限和冻结状态。原宿主全链路仍待部署后的现场验收，不以测试客户端替代。
