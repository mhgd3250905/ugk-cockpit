# 会话信息恢复：修复计划与验收

## 目标与边界

聊天遗失历史 MCP 返回值后，Agent 能通过平台重新核对当前会话和最新 revision，不要求用户记编号、翻旧聊天或重新 init。平台是会话状态事实源；聊天摘要不是身份凭据。

本轮基线为 `6ca91e92f5430ad848b15e8a5880567d679e5522`（`0.1.0-alpha.31`）。只修改 Cockpit 本仓库及相关技能，不修改产品仓库、真实会话或业务数据库，不执行接力、合并、清理、push 或发布。

## 行为契约

- 新增只读 MCP 会话查询，由 bridge 注入当前工作目录；Agent 不传本地路径或 token。
- 服务端重新核对目录授权、仓库身份、工作副本、会话状态及现有写入归属，返回真实 sessionId 和最新 revision。
- 查询不创建会话、不取得或转移写入权限、不续心跳、不递增 revision、不写业务操作记录。
- 查询到候选会话不等于取得操作授权。只有有效客户端绑定才自动继续；无绑定或身份不明时明确要求确认，不静默接管。
- 客户端绑定不得仅依赖聊天记忆。普通上下文压缩后仍可恢复；新客户端或绑定遗失时不能把目录相同当作同一聊天的证明。
- 等待新聊天接手、已经结束、位置身份改变和绑定过期不能报告为可继续。新聊天接力成功后，旧客户端不能借查询最新 revision 恢复旧权限。
- 查询与写入之间仍使用现有 revision CAS。冲突后不自动刷新 revision 重放写操作；传输结果不确定时保留原幂等请求的重试规则。
- relay、progress、handoff 及 closeout 的可选平台登记统一使用此恢复入口；closeout 本地成果不因查询失败而失效，submit 无需提前 init 的契约不变。

## 实施阶段

1. Luna Max 核对现有授权及会话接口，提出最小查询契约与客户端绑定策略，由主会话确认。
2. Luna Max 实现 core / HTTP / MCP 链路、技能与对应回归检查；先验证核心场景和受影响范围。
3. 主会话独立审查实现和技能行为，精确返修；稳定后由 Luna Max 执行一次完整 `npm test` 与 `npm run test:phase0`。
4. 更新版本及事实记录，核对安装副本与客户端生效条件，按实际完成情况报告。不得以临时夹具测试冒充真实项目已生成接力。

## 已批准的查询与确认方式

`ugk_work_context` 默认传 `{}`。客户端在成功 init / accept / resume 后记住服务端返回的会话绑定，查询时由 bridge 内部注入，不让模型填写。绑定包含接力代际；后端使用现有 relay 记录判定，不新增数据库 schema。revision 每次由服务端读取，不依赖客户端缓存。

客户端没有绑定时只返回候选。用户明确确认继续该候选后，Agent 可传成对的 `confirmSessionId` 和 `expectedRevision` 再查询；这些值来自刚才的 MCP 响应，用户无需填写。只有同一唯一候选及 revision 仍匹配时才在当前 bridge 内存中建立绑定，不改变平台会话或 lease。查询到候选本身、普通 progress 成功都不能自动建立绑定。

被新接力超越的旧绑定、等待接手、多个候选或已结束状态不允许通过上述确认捷径恢复；必须按平台实际状态走正规处理。查询成功也不是任何 Git、终态 handoff 或跨聊天接力动作的新授权。

## 验收清单

- 同一已接入客户端丢失聊天内 sessionId/revision，查询仍返回当前状态，随后可准备标准接力。
- 进展已更新 revision，查询从数据库返回新值，而非缓存值。
- 查询前后会话、写入权限、心跳、revision 和业务操作记录保持不变。
- 无绑定、错误目录、其他工作副本、已结束、等待恢复和已被新接力超越的旧绑定均不会被误判为自动可继续。
- 查询后发生并发更新，原写请求仍被 CAS 拒绝，且不隐式重试。
- 新 MCP 工具可发现，参数校验禁止模型注入路径/绑定字段；技能不再因缺少历史返回值直接要求重新 init。
- 全部修改只在本仓库和专门临时夹具验证；真实产品代码、会话和数据库未参与写入测试。
